# ApiStation FinOps 产品与技术设计

**文档版本：** v0.2（CNY 单账与生产接入稿）  
**日期：** 2026-07-26  
**项目目录：** `apistation-finops`  
**适用对象：** 站长、运营、财务核算人员、开发与运维人员

> 结论先行：建议建设一个独立的 ApiStation FinOps 管理服务。它不参与 API 转发和扣费主链路，只读同步 ApiStation 的用量、充值、用户、账号和分组数据，并维护独立的采购成本、费用、分摊与对账台账。在当前约 98 个用户、25 个上游账号、近 24 小时约 9,470 次请求的规模下，2C4G/30M 可以承载，但必须使用增量同步和预聚合，禁止在看板请求中反复全表扫描 `usage_logs`。充值、余额、用户扣费、上游实际成本、确认收入和利润统一使用 CNY；USD 只作为模型 Token 目录价值与优惠参考，绝不形成第二套余额或经营账。

## 1. 背景与决策

### 1.1 当前真正缺少的不是“统计图”，而是统一核算口径

现有 ApiStation 已经保存了请求、Token、用户扣费、账号、分组倍率、支付订单等大量原始数据，也有模型、分组、账号、用户等维度的用量统计。然而当前界面主要展示“实际、成本、标准”等技术计费字段，尚未把以下业务事实串成一套可以核对的经营账：

- 用户付了多少钱，支付渠道实际到账多少；
- 给用户增加了多少余额，其中多少是现金充值、赠送、兑换码、返利或人工调整；
- 用户已经消耗了多少余额，形成了多少管理口径收入；
- 上游账号是按量付费、预付余额、月租订阅还是一次性购买；
- 每个账号真实花了多少钱，费用覆盖哪个期间，如何分摊给用户和模型；
- 某个用户、账号、分组或模型到底贡献了多少毛利，哪些业务正在亏损；
- ApiStation 的扣费结果、用户余额、支付订单和 FinOps 台账是否一致。

因此，新系统的定位应是“经营核算与用量分析系统”，而不是简单增加几个图表。

### 1.2 建议决策

建设独立项目 **ApiStation FinOps**，采用旁路架构：

1. ApiStation 继续作为用户、账号、请求路由、用量记录和余额扣减的唯一业务主系统。
2. FinOps 只读同步 ApiStation 数据，不修改用户余额、不改变路由、不阻塞请求。
3. FinOps 自己维护 CNY 账号采购成本、其他费用、成本规则、CNY 余额批次、收入确认、分摊结果和经营报表；USD Token 价值只作为展示参考。
4. 第一阶段按分钟增量同步；第二阶段若需要秒级和强一致，再在 ApiStation 中增加事务型 Outbox 事件。
5. 生产接入不要求本地连接线上数据库或提供主库密码；由服务器管理员配置专用最小权限角色，先做 Schema 预检，再做连续 7 天只读影子同步。
6. 经营看板全部查询 FinOps 聚合表，不直接扫描 ApiStation 大表。

### 1.3 项目目标

- 让站长在 1 分钟内回答“今天收了多少、消耗了多少、花了多少、赚了多少”。
- 支持用户、API Key、账号、供应商、分组、渠道、模型、端点、计费模式、时间等维度分析。
- 对每个上游账号标记成本类型、采购批次、价格、币种、生效期、供应商和标签。
- 同时展示现金口径、消耗口径、估算成本口径和完全成本口径，避免混算。
- 支持充值、退款、返利、赠送、人工调账、账号采购和其他支出的可追溯台账。
- 通过对账中心发现漏单、重复扣费、余额异常、成本规则缺失和数据同步延迟。

### 1.4 非目标

- v1 不替代 ApiStation 的支付、余额、扣费、账号调度或认证功能。
- v1 不作为法定财务会计系统，不生成税务凭证或法定利润表。
- v1 不承诺从所有上游平台自动拉取账单；没有接口的供应商先支持人工录入或文件导入。
- v1 不修改历史 `usage_logs`，所有成本修订通过版本化规则和冲正记录完成。

## 2. 现状评估

### 2.1 截图反映出的信息断层

| 界面 | 已有能力 | 目前无法直接回答的问题 |
|---|---|---|
| 管理仪表盘 | 请求、Token、模型分布、账号数、用户数、三种费用数字 | 三种费用的业务含义、现金收入、采购支出、毛利及差异来源 |
| 用户管理 | 余额、今日/近 30 天用量、充值入口 | 累计现金充值、赠送余额、已确认消耗、服务成本、用户毛利、余额对账 |
| 分组管理 | 用户计费倍率、账号数量、今日/累计用量 | 分组收入、上游成本、折扣影响、毛利率是否低于阈值 |
| 账号管理 | 使用窗口、请求和 Token、系统估算扣费、调度信息 | 账号购买价、供应商、采购日期、有效期、剩余额度、摊销、闲置成本和回本情况 |
| 返利记录 | 邀请人、被邀请人、充值、支付、返利 | 返利是否计入获客成本，返利后该用户的真实贡献利润 |
| 使用记录汇总 | 模型/分组/端点的请求、Token 和费用 | 费用与充值、采购台账之间的桥接，无法形成经营闭环 |
| 请求明细 | 用户、Key、账号、模型、Token、两套费用 | 标签含义不够清楚，无法追溯对应成本规则和成本版本 |

### 2.2 代码中可复用的数据基础

现有代码已提供良好基础，主要包括：

- `usage_logs` 是只追加用量事实表，保存用户、API Key、账号、请求、模型、分组、订阅、输入/输出/缓存 Token、图片/视频用量、耗时和时间戳。
- `total_cost` 表示模型 Token 标准 USD 目录价值，只用于用户优惠感知和分析参考；`actual_cost` 表示受分组或用户专属倍率影响的用户 CNY 实际扣费。
- 源系统账号统计参考采用 `COALESCE(account_stats_cost, total_cost) * COALESCE(account_rate_multiplier, 1)`；源码确认 `account_stats_cost` 与 `total_cost` 同属 USD 定价单位，因此不得直接进入人民币成本或利润。
- 账号 `rate_multiplier` 已在请求产生时保存快照，能够避免后续修改倍率时污染历史数据。
- `payment_orders` 保存充值面额、实际支付金额、费率、支付方式、订单状态、支付时间、退款金额及供应商快照。
- `redeem_codes` 和余额历史可以识别兑换码、管理员加减余额等非在线支付变动。
- `users.total_recharged`、用户余额、API Key 配额与用量可用于总量核对。
- 已有小时/日仪表盘聚合表和大量统计查询，可以参考，但现有代码也明确标记了大表全量扫描的性能风险。

### 2.3 当前字段的命名风险

现有前后端语境中“实际成本”可能指账号口径费用，也可能指用户实际扣费。新系统不沿用模糊名称，统一采用以下显示文案：

| ApiStation 原字段/公式 | FinOps 显示名称 | 说明 |
|---|---|---|
| `total_cost` | Token 标准价值（USD 参考） | 写入 `standard_cost_usd_reference`，仅用于展示/优惠参考，不参与 CNY 账本或利润 |
| `actual_cost` | 用户实际扣费（CNY） | 本次请求从用户钱包或订阅额度中扣除的人民币余额，写入 `user_charge_cny` |
| `COALESCE(account_stats_cost,total_cost) * account_rate_multiplier` | 账号定价参考（USD） | 只可辅助核对，当前同步器忽略其 CNY 成本推导，不能直接写入成本或利润 |
| `account_cost_periods` 手工采购/供应商账单分摊 | 上游实际成本（CNY） | 直接登记人民币采购金额、手续费和税费后按期间分摊；缺失时标记待补 |
| `payment_orders.amount` | CNY 入账余额/订阅金额 | `order_type=balance` 时为人民币钱包入账额；订阅订单单独进入订阅账 |
| `payment_orders.pay_amount` | CNY 用户实付 | 支付渠道实际收到的现金；不等于入账额度 |
| `refund_amount` | CNY 余额退款 | 源系统记录的是余额退款；现金退款按 `pay_amount * refund_amount / amount` 计算 |
| `usage_logs.billing_type` | 钱包/订阅计费模式 | `0` 钱包余额，`1` 订阅额度；两者不可混入同一确认收入桶 |

## 3. 可行性分析

### 3.1 结论

**有条件可行。** 当前规模较小，新增一个轻量 Node.js 管理服务不会成为主要负担；30M 带宽对统计元数据足够。主要风险是 2 核 CPU 与 4GB 内存下，统计查询和 ApiStation 转发争抢 PostgreSQL、CPU 和磁盘 I/O。

满足以下条件后可以在同一台服务器部署：

- FinOps 不部署第二套 PostgreSQL 和 Redis；
- FinOps 应用为一个 Node.js 单服务容器，前端静态文件由同一进程托管；
- 连接池最大 5 个连接，后台同步批量化且限速；
- 看板只查小时/日聚合，不在请求时扫描原始用量表；
- PostgreSQL 与 FinOps 表按时间建立索引，明细表按月分区；
- 至少保留 20GB 可用磁盘，配置异机备份；
- 建议增加 2GB swap 作为 OOM 保护，但不把 swap 当正常内存使用；
- 上线前压测需确认 ApiStation P95 延迟没有明显回退。
- 线上连接使用独立 `finops_app` 角色：对 `public` 源表列级只读，对 `finops` Schema 可写；不使用主库管理员账号。
- 先完成 `information_schema`/目录权限预检和有限抽样，再进入 7 天影子同步；影子期不作为正式结算依据。

### 3.2 建议资源预算

| 组件 | 建议常态内存 | CPU 策略 | 说明 |
|---|---:|---:|---|
| PostgreSQL | 900-1,200MB | 优先 | 同时服务主系统与 FinOps，保留页缓存 |
| ApiStation | 800-1,300MB | 优先 | API 转发和计费主链路，不受统计任务阻塞 |
| Redis | 128-256MB | 低 | 设置合理 `maxmemory`；复用现有实例 |
| FinOps | 150-300MB | 上限约 0.5 核 | 连接池 5，增量同步和聚合限速 |
| 反向代理、Docker、系统 | 700-1,000MB | - | 包含内核页缓存和运维余量 |

以上是目标预算而非硬性保证。若 ApiStation 高峰时内存已超过约 2.5GB，或原始用量超过每日 20 万请求，应优先扩容到 4C8G 或拆分数据库，不建议硬塞第二个服务。

### 3.3 存储与保留策略

- 不复制用户代理、IP、请求体、响应体和账号凭证等无关大字段。
- 请求级 FinOps 明细默认保留 180 天，按月分区；超过期限可归档或删除。
- 小时聚合保留 400 天；日聚合和财务台账长期保留。
- 以当前约 1 万请求/天估算，年请求级数据约 365 万行，采用精简字段和正确索引可以承受。
- 磁盘空间是尚未提供的关键前提，部署前必须实际检查，而不能仅依据 2C4G/30M 判断。

### 3.4 风险与措施

| 风险 | 影响 | 措施 |
|---|---|---|
| FinOps 全表扫描 `usage_logs` | 转发延迟、CPU/IO 飙升 | 游标增量同步、预聚合、查询超时、低峰补数 |
| 直接写 ApiStation 表 | 余额或计费事故 | 独立只读数据库账号；FinOps 永不写源表 |
| 成本规则修改污染历史 | 报表前后不一致 | 成本规则版本、生效区间、请求快照、冲正而非覆盖 |
| CNY 余额与 USD Token 参考混算 | 利润失真 | USD 只显示 `standard_cost_usd_reference`，不进入余额、成本、收入、FIFO 或利润公式 |
| 将 `account_stats_cost` 当作 CNY 成本 | 虚构成本或利润 | 明确其为 USD 定价参考；CNY 成本只来自 `account_cost_periods`，缺失时标待补 |
| 固定订阅账号无请求时成本丢失 | 高估利润 | 记录期间采购成本与未分摊闲置成本 |
| 支付订单、兑换码、人工调账分散 | 无法对账 | 统一来源事件和经营台账，保留来源表与来源 ID |
| 源项目升级改表 | 同步中断 | Schema 兼容检查、启动自检、迁移版本白名单和告警 |

## 4. 核算口径设计

### 4.1 单一 CNY 账本，订阅单独核算

**CNY 现金/经营/钱包账：** 记录用户 CNY 实付、钱包余额增加/扣减、现金退款、支付手续费、账号采购、供应商充值、订阅采购、其他费用，以及按消费确认的人民币经营收入和利润。用户余额与 `actual_cost` 以 CNY 核算；上游成本只接受手工登记的人民币采购或供应商账单金额，并按有效期间分摊。

**USD Token 参考值：** `total_cost` 被同步为 `standard_cost_usd_reference`，只用于展示模型 Token 标准 USD 目录价值、折扣感知和权重分析。它不是余额、费用、收入、利润或可兑换货币，不参与 FIFO 和任何 CNY 守恒公式。

**订阅权益：** 订阅收款、订阅有效期、订阅额度和订阅用量单独记录。订阅现金可以进入 CNY 现金账，但在完成有效期/天数分摊前不并入钱包确认收入，避免把预收款提前当作利润。

充值当天只确认 CNY 现金流入和 CNY 余额入账；钱包经营收入在 CNY 余额实际消耗时通过 FIFO 批次确认。

### 4.2 核心指标与公式

| 指标 | 建议公式 | 用途 |
|---|---|---|
| 现金净流入 | 用户实付 - 现金退款 - 支付通道手续费 | 看资金是否增加 |
| 新增 CNY 余额 | 充值入账 + 赠送 + 兑换码 + 人工增加 - 人工扣减 | 看承担了多少服务义务 |
| 钱包确认收入（CNY） | 现金充值额度批次按 FIFO 被消费的比例 × 该批次净实付 CNY | 现金主账的管理口径收入，不称法定营业收入 |
| 订阅确认收入（CNY） | 订阅实付按有效期/天数分摊，单列展示 | 不与钱包确认收入混算 |
| 用户实际扣费（CNY） | `SUM(user_charge_cny)`，按 `billing_type` 分列 | 用户 CNY 余额消耗，钱包用量再通过 FIFO 确认收入 |
| Token 标准价值（USD 参考） | `SUM(standard_cost_usd_reference)` | 仅辅助观察模型目录价和优惠幅度 |
| 已归集上游成本（CNY） | `account_cost_periods` 中人民币采购/供应商账单分摊后的 CNY 合计 | 真实经营成本；没有成本记录时显示“待补” |
| 采购完全成本 | 账号采购/订阅/充值/手续费/税费按期间与用量分摊 | 回答真实花费由谁承担 |
| 贡献毛利 | 钱包确认收入 + 订阅确认收入 - 已归集上游成本 | 仅在成本覆盖完整时计算；缺失成本时显示“待核算” |
| 完全毛利 | 钱包确认收入 + 订阅确认收入 - 已分摊采购成本 - 可归属其他成本 | 判断真实经营结果 |
| 毛利率 | 完全毛利 /（钱包确认收入 + 订阅确认收入）；收入为 0 时显示不可计算 | 排序与告警 |
| 未消耗余额 | 期初余额 + 新增余额 - 已消耗 - 退款/扣减 ± 调整 | 用户余额对账 |
| 闲置成本 | 期间采购成本 - 已分摊成本 | 暴露空置账号、浪费和过度采购 |

### 4.3 币种与单位规则

- CNY 是唯一的钱包、现金、成本、收入和利润单位；`BASE_CURRENCY`、`BILLING_UNIT` 与 `SOURCE_BALANCE_UNIT` 均固定为 `CNY`。
- 用户充值、`users.balance`、`payment_orders.amount`、`usage_logs.actual_cost` 与 `user_charge_cny` 都按 CNY 处理。
- `total_cost` 仅保留为 `standard_cost_usd_reference` / `tokenListValueUsd`。它只可与 Token、模型和用户优惠参考并列展示，不能换算、相加或相减进 CNY 账。
- 充值订单同时保存 `pay_amount`（CNY 实付）和 `amount`（CNY 余额入账/订阅金额）；两者允许因赠送或折扣不同，但必须分列。
- 源 `account_stats_cost`/`total_cost` 不进入 CNY 成本；真实人民币成本只从 `account_cost_periods` 的采购/账单分摊读取。
- 人工账号成本和资金流水只允许 CNY，`fx_rate` 固定为 1，`base_amount` 由人民币原始金额派生；不得通过任何 USD→CNY 参数生成成本。
- 每个 API、列表、导出和 CSV 字段都带币种/单位后缀；禁止在 SQL 或前端将 CNY 账本字段与 USD Token 参考值求和或相减。

### 4.3.1 钱包额度批次与 FIFO 收入确认

每次余额增加都生成一个 `credit_lots` 批次，至少区分现金充值、兑换码、赠送、返利和人工调账，并保存入账 CNY、来源订单、现金基础 CNY、入账时间和剩余额度。钱包用量按发生时间从最早未耗尽批次开始分配：

`本次现金确认收入 CNY = 消耗额度 / 批次原始额度 × 批次净实付 CNY`

赠送、返利和人工调整批次的现金基础为 0，消费时只减少 CNY 余额并单列营销/调整消耗。退款只冲减未消费余额；源系统 `refund_amount` 是 CNY 余额退款，现金退款按 `pay_amount * refund_amount / amount` 计提并保留原订单关联。重复同步必须保持批次和收入确认幂等。

### 4.4 账号成本类型

| 成本类型 | 必填信息 | 推荐核算方式 |
|---|---|---|
| 上游按量后付费 | 供应商、人民币账单金额、账单周期、手续费/税费 | 以已登记的 CNY 供应商账单为准；无账单时标记待补，不自动估算利润 |
| 上游预付余额 | 人民币充值金额、获得额度、手续费、日期 | 以供应商余额扣减/账单和采购批次的 CNY 金额分摊；缺失记录时待补 |
| 固定周期订阅 | 购买金额、开始/结束、套餐、账号 | 日均摊销形成期间成本，再按用量权重分配 |
| 一次性购买账号 | 购买金额、预计可用期/到期日、残值 | 在可用期间摊销；提前失效时确认剩余损失 |
| 免费/自有资源 | 成本 0、原因、有效期 | 保留 0 成本依据，不与“未配置”混淆 |
| 混合成本 | 固定费 + 超额按量费 | 分别记录固定和变量成本后汇总 |

### 4.5 固定成本分摊

一个固定订阅账号既有“每天真实发生的采购成本”，又有“每个请求的占用贡献”。系统应同时保留两个视角：

1. **定价参考视角：** 请求保留 ApiStation 的 `total_cost`/`account_stats_cost` 和倍率快照，只用于模型定价、优惠与路由参考，不标记为 CNY 毛利。
2. **完全成本视角：** 将有付款/账单依据的账号期间 CNY 采购成本按天摊销，再按该账号当天各请求的标准目录价值权重分配给用户、模型和分组。

默认公式：

`请求分摊成本 = 当日账号摊销成本 × 本请求标准目录价 / 当日该账号标准目录价合计`

当账号当天没有请求时，当日成本全部进入“闲置成本”，不强行分给用户。管理员可选择 Token 权重、请求数权重或自定义权重，但修改只对新成本版本生效。

### 4.6 更正原则

- 财务与成本记录只追加，不直接删除或覆盖已入账记录。
- 更正通过一笔反向冲正和一笔正确记录完成，并引用原记录。
- 成本规则带版本号、审批人、生效起止时间和创建时间。
- 重算任务必须显示影响范围、旧值、新值、差额和操作者。

## 5. 用户与权限

### 5.1 角色

- **超级管理员：** 配置数据源、币种、权限、成本规则和系统参数。
- **运营管理员：** 查看全部经营数据，维护账号采购和其他费用，执行对账与导出。
- **只读分析员：** 查看授权报表，不能修改成本和发起重算。
- **审计员（后续）：** 查看变更、冲正和导出历史，不能查看账号凭证。

v1 默认只服务内部管理员，不向终端用户开放。若以后开放用户自助用量页，应走独立权限接口，只返回当前用户数据。

### 5.2 安全边界

- FinOps 不读取或存储 `accounts.credentials`。
- 示例统一使用独立 `finops_app` 角色：对 `public` 只授予所需列的 `SELECT`，对 `finops` Schema 授予应用写权限；不得复用 PostgreSQL 管理员或 `sub2api` 主应用账号。
- `public.settings` 可能包含 SMTP、验证码和 OAuth 密钥，`finops_app` 不得读取该表或 `key/value` 列；数据库管理员在独立 `finops_source` Schema 中拥有 `security_barrier` 视图 `balance_recharge_multiplier`，只暴露 `BALANCE_RECHARGE_MULTIPLIER` 一行，应用仅获得该视图的 `SELECT`。
- 连接串只保存在服务器环境变量或 Docker Secret，不发给开发人员，不写入代码仓库。
- 管理端复用统一登录或独立管理员登录均可，建议第一版复用 ApiStation 管理员 JWT 并增加服务端角色校验。
- 成本、手工流水、导出和重算均写审计日志。

## 6. 功能架构与页面设计

### 6.1 经营总览

目标是让站长在一个页面读懂经营状态，默认时间范围为“今天”，可切换昨日、近 7 天、近 30 天、本月和自定义区间。

核心指标分成三行而不是混在一组卡片：

- **现金（CNY）：** 用户实付、现金退款、通道费、采购支出、现金净流入；
- **经营（CNY）：** 钱包 FIFO 确认收入、订阅期间确认收入、已归集采购/账单成本、待补成本、贡献毛利、完全成本、完全毛利、毛利率；
- **钱包（CNY）：** 充值入账、赠送/返利、当前余额、钱包/订阅实际扣费；
- **参考值（USD）：** Token 标准目录价值，仅用于展示模型牌价和优惠感知；
- **用量：** 请求、成功率、输入/输出/缓存 Token、活跃用户、活跃账号、平均延迟。

核心图表：

- 收入、估算成本、完全成本和毛利趋势；
- CNY 现金充值、额度入账、FIFO 确认收入和未消耗余额桥接图；
- 用户、账号、模型、分组毛利 Top/Bottom；
- 成本结构：固定采购、按量、支付手续费、返利、其他费用；
- 待处理告警：缺失成本、负毛利、未对账订单、同步延迟、闲置账号。

### 6.2 用户账务与利润

列表字段：用户、标签、现金充值（CNY）、入账余额（CNY）、赠送/返利（CNY）、钱包确认收入（CNY）、订阅确认收入（CNY）、实际扣费（CNY）、Token 标准价值（USD 参考）、请求、Token、已归集上游成本（CNY）、成本覆盖状态、完全分摊成本（CNY）、毛利（CNY）、毛利率、当前余额（CNY）、最后活跃时间。成本缺失时毛利显示“待核算”，不能按 0 成本制造虚高利润。

用户详情包含：

- 收入/成本/毛利趋势；
- 模型、分组、API Key、账号、端点分布；
- 充值、退款、赠送、返利、人工调账时间线；
- 用户余额对账公式和差额；
- 请求明细下钻，展示计费规则版本和成本来源；
- 导出该用户的用量与资金明细。

### 6.3 账号台账与成本

列表字段：账号、平台、供应商、成本类型、采购批次、有效期、采购金额（CNY）、累计请求/Token、用户实际扣费（CNY）、Token 标准价值（USD 参考）、已归集上游成本（CNY）、成本覆盖状态、已分摊采购成本（CNY）、闲置成本（CNY）、回收率、毛利（CNY）、状态和标签。

账号详情包含：

- 采购档案：供应商、订单号、人民币金额、手续费、税费、生效期、附件备注；
- 成本规则：按量、预付、固定订阅、一次性购买、混合；
- 用量窗口与成本趋势；
- 使用该账号的用户、模型、分组贡献；
- 成本摊销计划、已摊销、未摊销、闲置成本；
- 上游账单与系统估算差异；
- 到期、余额不足、异常消耗和长时间闲置告警。

支持账号标签：供应商、采购渠道、批次、负责人、地区、质量等级、是否共享、成本中心、自定义标签。标签必须保存历史快照，避免改标签后历史报表整体漂移。

### 6.4 供应商与采购

供应商页面按上游归集账号、平台、请求、Token、钱包/订阅确认收入（CNY）、用户实际扣费（CNY）、Token 标准价值（USD 参考）、已入账/已分摊上游成本、期间采购、待补成本、完全毛利和毛利率，并明确显示未绑定账单/采购记录、未标记供应商和即将到期账号。

采购批次台账至少包括账号、供应商、批次、成本模板、人民币成本、手续费、税费、生效期和状态。采购成本与现金支出需要建立稳定关联；首版允许双录并在对账中心暴露未关联差异，后续改为一次提交同时生成成本期间和现金流水。

### 6.5 用量与扣费

统一筛选器：时间、粒度、用户、API Key、账号、供应商、平台、渠道、分组、模型、请求模型、上游模型、端点、计费模式、请求类型和标签。

指标包括：

- 输入、输出、缓存创建、缓存读取、图片、视频等用量；
- 请求数、成功/错误数、首字延迟、总延迟；
- Token 标准目录价值（USD 参考）、用户实际扣费（CNY）、已归集上游成本（CNY）与成本覆盖状态；
- 单百万 Token 收入/成本、单请求收入/成本；
- 缓存命中率、长上下文占比、模型映射差异；
- 同比、环比和累计占比。

请求明细必须明确显示用户实际扣费（CNY）、Token 标准价值（USD 参考）、已入账成本（CNY）和成本覆盖状态。没有账号成本期间时显示“成本待补”，不得用模型定价公式生成上游人民币成本。

### 6.6 充值与资金

分为四个页签：

1. **支付订单：** 成功、待支付、失败、退款，区分入账余额（CNY）和实付（CNY），显示赠送/折扣倍率、通道、费率和订单生命周期。
2. **余额变动：** 现金充值批次、兑换码、赠送、返利、管理员增加/扣减、钱包消费扣费、订阅权益；显示来源批次和 FIFO 消耗顺序。
3. **采购支出：** 账号购买、供应商充值、订阅续费、代理、服务器、手续费及其他成本。
4. **现金日报：** 当日流入、流出、净流量和支付渠道对账差额。

### 6.7 成本核算

- 创建成本模板并批量绑定账号；
- 设置成本类型、人民币固定费、变量费、生效时间和分摊方法；
- 支持按账号、账号标签、平台、渠道、模型和供应商配置优先级；
- 规则冲突时按“账号精确 > 标签 > 渠道/平台 > 全局默认”匹配；
- 提供规则试算：输入一条历史请求，展示命中规则和计算结果；
- 上线规则前显示影响账号数和预计历史差额，保存后形成新版本。

### 6.8 对账中心

对账任务按日自动执行，也可手工重跑：

- 支付对账：成功订单、退款、面额、实付与支付渠道流水；
- 余额对账：期初余额 + 增加 - 消耗 - 减少 = 期末余额；
- 用量对账：FinOps 聚合与 ApiStation `actual_cost`、Token、请求数一致；
- 成本对账：请求级估算成本之和与账号/渠道汇总一致；
- 采购对账：期间采购成本 = 已分摊成本 + 闲置成本 + 未到生效期成本；
- 数据完整性：缺失用户、账号、模型价格、成本规则或来源记录。

每个差异必须能下钻到来源表、来源 ID、计算规则和差额，不只显示“失败”。

### 6.9 数据同步

- 按用户与账号、用量与扣费、充值与退款、兑换码与返利、订阅、自动对账等来源展示状态；
- 展示最近成功时间、当前游标、最大延迟、累计行数和最近错误；
- 同步失败必须写入状态台账，不能只打印服务日志；
- 展示 Schema 预检结果、字段缺失、权限缺失和 `/ready` 状态；支持受限手工重跑与可暂停/续传的历史回填。

### 6.10 告警、报表与导出

- 日报、周报、月报：现金、消耗、成本、毛利、用量和异常摘要；
- 用户利润表、账号回本表、模型毛利表、分组折扣效果表、供应商成本表；
- CSV/XLSX 导出遵循当前筛选条件，记录导出人、时间和范围；
- 告警支持站内、邮件或 Webhook：负毛利、毛利率过低、成本缺失、账号即将到期、闲置成本过高、同步延迟、对账差异；
- 大导出走后台任务，避免阻塞 Web 请求。

## 7. 数据架构

### 7.1 数据流

`ApiStation PostgreSQL（finops_app 对 public 列级只读） -> CNY 单位与 Schema 预检 -> 增量同步器 -> FinOps CNY 事实/台账 + USD Token 参考 -> 小时/日聚合 -> API -> 管理前端`

同步器按来源维护独立游标：

- 只追加表按 `(created_at, id)` 增量读取；
- 可变订单按 `(updated_at, id)` 增量读取，并保留 10 分钟回看窗口；
- 每批默认 1,000 条，每分钟执行；
- 每轮最多执行 3 批，避免在 2C4G 主机上追赶历史时影响 ApiStation；
- 以 `source_system + source_table + source_id + source_version` 幂等去重；
- 同步失败不影响 ApiStation，请求恢复后自动续传；
- 每晚重算最近 3 天聚合，吸收迟到退款和人工调账；
- 生产首次接入先完成只读 Schema 预检，再连续影子运行 7 天，影子期不改变源系统行为也不作为正式结算依据。

### 7.2 建议数据表

| 表 | 用途 | 关键字段 |
|---|---|---|
| `sync_cursors` | 来源同步水位与状态 | source_name、cursor_time、cursor_id、lag、last_error |
| `source_audit_events` | 支付/审计来源索引 | source_table、source_id、action、occurred_at、detail |
| `dim_users` / `dim_accounts` | 当前维度与软删除状态 | source_id、status、deleted_at、标签/成本档案 |
| `fact_usage_events` | 精简请求级 CNY 核算事实 | source_usage_id、billing_type、tokens、standard_cost_usd_reference、user_charge_cny、recognized_revenue_cny |
| `fact_usage_daily` | 长期日聚合 | day + billing_type + 主要维度 + Token/金额指标 |
| `cash_transactions` | CNY 现金流入流出 | direction、order_type、pay_amount_cny、refund_amount_cny、source |
| `credit_events` | CNY 余额变动来源 | user_id、event_type、credit_amount（CNY）、cash_basis_cny、source |
| `credit_lots` | CNY 余额批次与 FIFO 剩余额度 | user_id、lot_type、granted_credit、remaining_credit、cash_basis_cny、credit_currency=CNY |
| `revenue_recognition` | 用量到额度批次的收入确认 | usage_id、credit_lot_id、consumed_credit、recognized_revenue_cny |
| `cost_profiles` / `account_cost_periods` | 成本策略与采购期间 | type、allocation_method、currency=CNY、effective_range、amount/fee/tax |
| `reconciliation_runs` / `audit_logs` | 对账批次与管理审计 | type、period、status、difference、actor、action |

所有货币字段在 PostgreSQL 使用 `NUMERIC`，Node.js 端使用 `decimal.js` 做十进制定点计算，不使用 JavaScript `Number` 做最终台账金额计算。

### 7.3 来源映射

| ApiStation 来源 | FinOps 用途 | 注意事项 |
|---|---|---|
| `usage_logs` | 请求、Token、CNY 实际扣费、USD Token/账号定价参考 | 只追加；`total_cost` 与 `account_stats_cost` 均为 USD 定价单位，不是付款凭证，不进入 CNY 成本或利润 |
| `users` | 用户、CNY 当前余额、累计充值辅助字段 | 当前余额用于对账，不直接当作确认收入；`total_recharged` 不能替代支付订单实付 |
| `api_keys` | Key 维度和配额 | 软删除后仍需保留历史快照 |
| `accounts` | 账号维度与倍率 | 禁止读取 `credentials`；成本标签在 FinOps 维护 |
| `groups` / 用户专属倍率 | 售价规则解释 | 请求日志已有倍率快照时优先使用快照 |
| `payment_orders` | CNY 实付、余额/订阅入账、手续费、退款 | `paid_at` 是主要收款事实；余额与订阅按 `order_type` 分开，状态更新需要重复同步 |
| `finops_source.balance_recharge_multiplier` | CNY 充值入账倍率 | 管理员拥有的安全屏障视图，只返回一个非敏感设置；禁止读取 `public.settings` |
| `redeem_codes` / 余额历史 | 兑换、赠送、人工调账 | 必须区分现金与非现金来源 |
| `user_affiliate_ledger` | 返利额度与获客成本 | `accrue` 只记返利成本，`transfer` 才生成用户可消费额度批次 |
| `user_subscriptions` | 订阅有效期、额度与用量限制 | 订阅用量和收入单独于钱包账核对 |
| `channels` 及成本定价规则 | 模型/账号定价参考解释 | 保存规则版本和命中快照；不自动生成 CNY 上游成本 |

### 7.4 历史数据策略

- 首次上线回填最近 90 天请求明细和可获得的全部支付/余额历史。
- 更早数据若只有聚合，可标记为“历史估算”，不得伪装成请求级精确数据。
- 历史回填必须使用独立、可暂停、可续传的低优先级任务，按天切片并限制批次和查询超时；普通每分钟同步只负责增量追赶，不能替代首次回填任务。
- 回填完成后输出完整性报告：覆盖时间、记录数、金额差异、缺失规则和不可核算金额。
- 真实库接入前后都不需要从本地保存或传输主库密码；生产 `.env` 只落在服务器。
- 回填后进入 7 天影子同步：每日比较源表与 FinOps 的请求数、Token、CNY 实际扣费、CNY 现金、退款、FIFO 确认、上游 CNY 成本和订阅分摊；USD 只核对 Token 标准参考值，所有差异必须能下钻到来源 ID。
- FinOps 尚未在生产上线，首次正式部署只允许对新的空 `finops` Schema 执行 `001_init` 和 `002_cny_accounting`。若 `schema_migrations` 已存在旧 `002_dual_ledger`，迁移必须拒绝；先备份旧 `finops` 数据、人工核对其实际单位，再由数据库管理员重建干净 Schema 并重新预检，绝不自动把旧 USD Credit 数据改标为 CNY。

## 8. 技术方案

### 8.1 推荐技术栈

- 后端：Node.js 22 ESM，使用内置 HTTP 服务承载 API 和静态文件，`pg` 连接 PostgreSQL，`decimal.js` 处理金额；
- 前端：原生 HTML、CSS 和 JavaScript，由同一 Node.js 服务托管，沿用 ApiStation 左侧菜单与右侧数据工作区的管理端布局；
- 数据库：复用 PostgreSQL 实例，使用独立 `finops` 数据库或 Schema；
- 缓存：v1 不依赖 Redis，必要的短缓存使用进程内缓存；
- 图表：浏览器原生 Canvas，首版不额外引入图表框架；
- 部署目标：Docker Compose，单个 FinOps 镜像同时运行 API、同步器和静态管理前端；
- 路由：建议使用独立子域名 `finops.example.com`，避免与 ApiStation 前端路由冲突。

### 8.2 为什么不直接改 ApiStation

- 成本与财务规则变化频繁，和高可用转发主链路的风险等级不同；
- 旁路系统失败不会影响用户调用和扣费；
- 可以独立升级、回填和重算；
- 通过只读权限降低误改余额和账号数据的风险；
- 开源上游升级时，减少长期维护大规模 fork 的成本。

需要承认的代价是数据会有约 1-2 分钟延迟，且源表结构升级需要兼容检查。对经营分析而言可接受。

### 8.3 部署拓扑

同一 Docker 网络内运行：

- `sub2api`：现有应用；
- `postgres`：现有数据库实例，新增 `finops` Schema；`finops_app` 对 `public` 列级只读、对 `finops` 可写；
- `redis`：现有缓存，不供 FinOps 强依赖；
- `apistation-finops`：新增 Node.js 单服务应用，内部端口 8090，只绑定宿主机 `127.0.0.1`；
- Caddy/Nginx：将独立子域名反代到 FinOps。

建议参数：FinOps 单进程运行、`NODE_OPTIONS=--max-old-space-size=256`、容器内存上限 384MB、CPU 上限约 0.75 核、数据库最大连接 5、空闲连接 2、同步批次 1,000、每轮最多 3 批、同步周期 60 秒、查询超时 10 秒、后台重算单并发；Compose 日志轮转为 3 个 10MB 文件，外部 Docker 网络必须填写服务器实际存在的网络名。

### 8.4 性能目标

- 总览与常用列表 P95 小于 2 秒；
- 请求明细 P95 小于 3 秒；
- 默认同步延迟小于 2 分钟；
- 日对账在当前规模下 10 分钟内完成；
- FinOps 后台任务运行时，ApiStation P95 延迟增幅不超过 10%；
- 任何看板查询最多扫描限定日期的分区或聚合表。

### 8.5 可观测性与运维目标

- `/health`（已实现）：返回进程状态、演示/数据库模式和运行时间；
- `/ready`（已实现）：Schema 版本、数据库连接和最近同步成功；来源列级权限由启动预检和部署验收确认；
- 指标：同步延迟、每批记录数、失败数、聚合耗时、查询耗时、对账差额、数据库连接；
- 日志带任务 ID 和来源游标，不记录用户密钥或账号凭证；
- 每日备份 FinOps Schema，支付/成本/台账保留异机备份；
- 启动时检查 ApiStation 必需表和字段，结构不兼容则拒绝同步并明确告警。

## 10. 验收标准

### 10.1 数据正确性

- 指定日期范围内，FinOps 请求数、Token、`actual_cost` 与 ApiStation 差异为 0；
- `users.balance`、`payment_orders.amount`、`usage_logs.actual_cost` 与 `user_charge_cny` 均按 CNY 对账；`standard_cost_usd_reference` 只作为 Token 参考值单独核验；
- 钱包用量按 `billing_type=0` 消耗额度批次，订阅用量按 `billing_type=1` 单独汇总，不发生跨账混分；
- 每个现金充值批次满足：原始额度 = 已消费额度 + 剩余额度 + 已退款/冲正额度；FIFO 确认收入可追溯到订单和用量 ID；
- CNY 现金退款严格使用 `pay_amount * refund_amount / amount`，并与支付订单原始额度、实付和退款额度保持比例一致；
- CNY 上游成本都能追溯到账号采购或供应商账单的人民币金额和分摊记录；没有依据的记录标记待补，`account_stats_cost`/`total_cost` 公式不进入 CNY 利润；
- 完成支付、退款、兑换、返利和人工调账均能追溯到来源 ID；
- 每个固定成本期间满足：采购成本 = 已分摊成本 + 闲置成本 + 未生效/未摊销成本；
- 所有人工成本和资金流水均通过 CNY-only 校验并可追溯到来源记录；
- 同一来源事件重复同步不会重复入账；
- 更正记录可追溯原记录，冲正前后总额守恒。

### 10.2 产品可用性

- 总览不再出现未解释的“实际/成本/标准”；每个指标都有口径说明和计算展开；
- 从任一汇总数字最多三次点击可下钻到用户/账号/请求或资金来源；
- 筛选条件在图表、列表与导出中一致；
- 负毛利、缺失成本、同步延迟和对账差异有醒目标识；
- 金额始终显示币种，禁止不同币种直接相加。
- USD Token 标准价值只能作为参考列展示，页面、导出和 API 不得把它标为余额、成本、收入、利润或可用额度。

### 10.3 上线门槛

- 连续 7 天影子运行，对账结果稳定；
- 生产首次迁移为 `002_cny_accounting`；若检测到旧 `002_dual_ledger`，已完成备份、人工重建与 CNY 重核对，未发生自动 USD Credit 改标；
- 压测确认 FinOps 后台任务不会明显影响 ApiStation；
- 数据库备份和恢复演练通过；
- `finops_app` 对 `public` 的列级只读权限检查通过，无法读取 `accounts.credentials` 与 `public.settings`，且只能通过 `finops_source.balance_recharge_multiplier` 读取充值倍率；
- 管理操作、导出和重算审计完整；
- 成本规则和固定成本分摊口径由站长确认。

## 12. 已冻结默认值与后续可配置项

| 默认项 | 当前取值 | 影响 |
|---|---|---|
| 报表本位币 | CNY；USD 只保留 Token 标准目录价值参考 | 所有现金和利润报表 |
| 用户余额单位 | CNY | 充值、余额、扣费与收入桥接 |
| USD Token 参考 | `standard_cost_usd_reference` / `tokenListValueUsd`，不参与账本 | 用户优惠感知与模型价格参考 |
| 钱包确认收入 | 现金充值额度批次 FIFO 消耗确认 CNY | 用户/模型钱包收入与利润 |
| 订阅收入 | 单列，按有效期/订阅天数分摊后确认 | 防止预收款提前计入利润 |
| 固定账号成本分摊 | 按天摊销，按标准目录价权重分配 | 用户/模型完全毛利 |
| 无请求日成本 | 计入闲置成本 | 避免虚高利润 |
| 请求明细保留 | 目标 180 天；清理任务实现并评审前不自动删除 | 磁盘与历史下钻 |
| 同步频率 | 60 秒，最近 10 分钟回看 | 实时性与数据库压力 |
| 历史回填 | 请求 90 天，资金记录尽可能全量；可暂停续传 | 首版上线速度 |
| 返利口径 | 单列获客/销售费用，同时计算返利后毛利 | 用户真实贡献 |
| 赠送额度 | 不算现金收入；消费时按管理口径单列赠送消耗 | 收入与营销成本 |
| 上游真实账单缺失 | 显示“估算成本”，禁止标成真实成本 | 报表可信度 |
| 管理端访问 | v1 仅内部管理员 | 权限与开发范围 |

首版开发已按上表默认值执行，不再作为开发阻塞项。后续接入上游真实 CNY 账单或开放更多角色时，再通过版本化配置调整，不回写污染历史结果。
